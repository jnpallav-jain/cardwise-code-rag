Evaluation report · September 2026

Retrieval reached 76% of the ceiling on 4% of the context

Retrieval-augmented search over a private multi-platform codebase — Kotlin, Swift and SQL — measured against a frozen thirty-question eval. Three chunking strategies landed within one question of each other. What the answer actually depended on was the kind of question asked.

Headline

Long-context is the ceiling, not the system

Both approaches scored on the same contract: the answer must cite every file it needed.

RAG — retrieve, answer, cite 19/30 ~7,700 tokens per question

Long-context is the measurement instrument here, not a candidate design: it sets the ceiling that makes RAG's 19/30 interpretable. Retrieval reached 76% of it on about 4% of the context. As a system you'd actually run, long-context fails three ways — cost scales with the corpus rather than the question; it depends on a warm cache (≈$0.05 a question on a hit, ≈$0.40 on a miss, against ≈$0.025 for RAG); and at around five times this codebase's size it no longer fits a 1M-token window at all.

The finding

Question type mattered far more than chunking

Same retriever, same corpus, same run. Finding a file scored 100%; tracing what calls it scored 20% — a 5× spread. Every chunking strategy tested moved the total by one question.

Long-context RAG end-to-end
Locate10 questions 100% 100%
Cross-platform5 questions 80% 60%
Explain10 questions 80% 50%
Trace5 questions 60% 20%
0%25%50%75%100%

The mechanism is plain once seen. A locate question has its answer in one file, and embedding similarity is good at finding one file. A trace question requires following a reference between files — AppState.kt:221 calls repository.recommend(), which reaches CardWiseRepository.kt:31, which instantiates the engine. An embedding scores each file independently. It cannot follow anything.

Every configuration

Two counterintuitive results

Deleting the file path improved retrieval

Every chunk carried a # File: <path> header so a chunk retrieved alone would still say what it was. It cost 8,913 tokens across 334 chunks — 27 tokens repeated on every fragment — about 7.4% of the corpus.

trace20%→60%

Tripled by deleting text — the same gain predicted to require a second retriever. Checked the obvious worry: strip every path and locate still scores 9/10, so that number was real retrieval, not filename matching.

BM25 alone scored 3/30

Lexical search should own trace questions — the answer is the file containing the literal identifier. Instead it collapsed. Every path holds the product name, so card appears in 272 of 334 chunks: the IDF signal that makes an identifier discriminating is destroyed by a codebase named after itself.

fused, trace1/5→4/5

Yet fused with dense retrieval it fixed what dense missed — a 10%-accuracy retriever rescuing a 53%-accuracy one.

Falsified

What I predicted wrong

Predictions 01 and 02 were committed before the BM25 code that tested them — checkable in git log. 03 and 04 were hypotheses stated during the work and then tested; they were not pre-registered.

01
“BM25 will lift trace above 60%.” Wrong as stated

BM25 alone left trace at 1/5. Fused with dense it reached 4/5 at equal context — but at recall@5, the metric actually specified, it stayed at 0/5. The prediction never named a metric, and the two metrics disagreed completely. Right about the mechanism, wrong about the measurement.

02
“The failure will be tokenization — BM25 won't split camelCase.” Wrong

The tokenizer worked on the first attempt: CardWiseComponents → {cardwisecomponents, card, wise, components}. The real cause was IDF collapse, which I had not considered at all.

03
“The file-path header is poisoning BM25.” Wrong

A clean, plausible diagnosis. Stripping the header moved BM25 from 3/30 to 4/30 — nothing. It did improve dense retrieval substantially, which is how the finding above was discovered: by testing a wrong hypothesis and reading the result carefully.

04
“Long-context will win big on trace — it can follow a call graph.” Wrong

Long-context and the best RAG arm both scored 3/5 on trace. The gap between them sits entirely in explain (80% vs 50%). A model that sees every file did not follow references better — it combined facts across files better.

Six measurement bugs, and which way each one pointed

  • max_tokens truncated answers before the citation line — scored as zero citations, indistinguishable from a wrong answer.
  • A thinking block consumed an entire 2,048-token budget and returned no text at all. Same silent zero.
  • tree-sitter cannot parse ON CONFLICT … DO UPDATE SET, present in every migration here — so “structural” SQL chunking was mechanical slicing wearing a parser's name.
  • Cutting only at top-level nodes turned a one-class Swift file into fixed-size chunks: structural chunking that wasn't.
  • Comparing retrieval recall against citation coverage flattered RAG by four questions — recall measures whether a file was available, coverage whether it was used. That one is why the headline reads 19/30 and not 23/30.
  • Token counts came from tiktoken and were reported as the model's — 113k, against the 193k Anthropic's tokenizer actually read. The one bug that flattered the baseline rather than RAG: long-context looked cheaper, and further from the context ceiling, than it is.
Method

Corpus, eval, and what to distrust

  • Corpus. 165 tracked files → 119 indexed: 113,256 tokens by o200k_base, 193,173 by Anthropic's tokenizer — the model counts this code 1.71× higher. Against o200k_base, an early len(text)//4 estimate ran 5% high in aggregate but −28% to +25% per file — enough to reorder which files got split.
  • Chunking. Structural via tree-sitter where the grammar parses, a hand-written scanner for SQL, fixed-size fallback on any parse error. Every file's fragments are asserted to reconcatenate into the original byte-for-byte before anything is written.
  • Eval. Thirty questions in four categories, frozen before the first run. Ten prose cells were resolved into concrete paths in a separate file — never by editing the frozen one — each carrying a confidence and a note where the resolution narrows or extends the original.
  • Store. A numpy array. At 119–334 chunks a vector database earns nothing.

n = 30. A one-question difference is noise. Only the 12-vs-19 and 19-vs-25 gaps are worth defending.

The long-context baseline is non-deterministic. Two runs disagreed on three questions. The retrieval arms are exactly reproducible; this is not.

Two best-performing configurations were found post-hoc — rrf body-only and no-header. They need held-out questions before they are load-bearing.

Cost figures are list-price estimates, and RAG's token count is extrapolated with the tokenizer ratio rather than measured on the API.

Source corpus is a private repository and is not published. Code, frozen questions, recorded predictions and per-run write-ups live in the project repo.
